# Known gaps

Accepted for the MVP; each is a deliberate limit, not a hidden defect.

- Reactions are deferred (FR-ING-07). REST polling cannot see reaction removals.
- EMPTY_CONTENT is counted and alerted, but it is not flagged in a column.
- Time-zone handling has a fixed-offset fallback; it does not use a full tz database.
- Relevance and proposal artifacts hash different text (see the W8 A5 report).
- W8 A5 hash finding: the proposal request hash covers the text without `mention_handle_map` while the stored artifact includes it; the response hash covers the full text but `raw_response` may be truncated at 64 KB, so neither hash can be recomputed from storage alone.
- There is no live loop until W8.
- There is no logging setup until W9.
- Delivery must run in exactly one process (the worker). `deliver_pending` treats any `SENDING` row as a lost claim and resends it, so two concurrent delivery processes could double-send; the duplicate is visible as `WORKER_CRASH_AFTER_SEND`.
- `ASSIGNEE_ACCEPTED`/`ASSIGNEE_DENIED` name the assignee with the most recent `agreed_at` for that agreement. The notification row stores the task and recipient, not the acting assignee, so two assignees accepting the same task cannot be attributed per notification row.
- A zero-recipient announcement stages no row, so every sweep re-examines it with one bounded query and no row churn. This is deliberate: no recipient is invented and no marker table is added.
- The notification schema has no OTP event or OTP row. Phase 12 calls `OtpSender.send` directly after resolving the roster Discord id; the delivery tick does not invent an OTP notification.
- FCM HTTP v1 and Discord DM sending have not been exercised against the real services. Tests use fake transports and a fake `TokenProvider`. The optional `push` extra is not declared in `pyproject.toml` because the owner pin was blank; installing and pinning it remains an owner step.
- API idempotency (owner A2, 0025): the response row is written in a separate transaction immediately after the service commit, so a crash between the two loses the stored response; a retry then re-runs the operation. The services used on idempotent routes are state-idempotent where possible (a second accept returns created=False, a second decision returns changed=False), but a claim retried after that window is refused with 409 rather than replayed.
- API idempotency: a 4xx is never stored, so a failed request is re-executed on retry; this is deliberate (a corrected request must be able to succeed) and means error responses are not byte-stable across retries.
- API idempotency: `cleanup_expired` is a function, not a scheduler; the API server never runs it, so expired rows remain until an operator deletes them in bounded batches.
- Session D owner decision A resolves the Session C NEEDS-OWNER cell: Admin's `PUSH_ANNOUNCEMENT` "—" is enforced by `authorize_proposal_acceptance`, which refuses an Admin's acceptance of an `ANNOUNCEMENT` proposal and records the denial against `PUSH_ANNOUNCEMENT`. No other Admin override changed.
- Role dashboards (owner decision E, D4) are a fixed-size view: every list is capped at `API_DASHBOARD_LIST_LIMIT` (default 50), `counts` carries the uncapped totals and `has_more` says whether the list was cut. The `attention` block is count-only (unread notifications, claimable open tasks, unfinished tasks, pending reviews, pending approvals) and deliberately does not add new lists; `/tasks` and the Admin ledger routes keep their own page caps.
- Admin dashboard specifics (owner decision B): counts are cumulative; `messages.last_24h` uses SQLite `julianday`, an unparsable `received_at` counts as not recent, `relevance.relevant/irrelevant` count distinct message ids with a decision, and a task's status is derived from its live accepted, non-cancelled assignments (no stored task-level status). The Admin view no longer exposes attempts, denials, evaluation or configuration; their separate Admin routes remain.
- The processing and delivery pauses (owner decision C, 0026) are cooperative: they stop the worker's next pipeline tick or next delivery hook, cannot interrupt an in-flight AI or sender call, and are not a host-level hard stop. Stopping the worker process itself remains a Phase 13 deployment operation. Ingestion is never paused.
- Exports (owner decision D, `backend/export.py`) are a point-in-time copy, not a backup: a read-only open of a WAL database may let SQLite create its `-wal`/`-shm` sidecars next to the source (the database file itself is never modified), and rows committed after the read snapshot are not in the files. Masking is shape-based: a value that resembles a phone, email, roll number or government ID is masked even when it is not personal data, and unmasked mode is an explicit operator choice that keeps free-text personal data while still excluding the credential stores and `person.roll_number`.
- A masked export masks each stored text value as text. A column that itself holds JSON (`raw_metadata`, `parameters_used`, `counts_json`, `expected_json`, `predicted_json`) is masked as a string, so a phone-like bare number inside it would become `[PHONE]` and the nested JSON would no longer parse; the outer JSON Lines file stays valid.
