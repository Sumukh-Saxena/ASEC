# SRS figures digest (companion to docs/SRS.md)

The SRS DOCX contains ten diagrams that `docs/SRS.md` cannot show. This digest transcribes their normative content. If it ever disagrees with the DOCX, the DOCX governs; report the difference.

**Figure 1 (context).** Discord adapter (REST polling: ingest, normalize, map group and sender) → Bucketer (per-group windows W, G, M, C) → closed buckets → Pipeline orchestrator (attempts, retries, PII masking, schema validation, name resolution) ↔ AI layer (stateless: relevance classifier, proposal generator, self-hosted model on Colab or local; "masked bucket in, results out") → validated proposals → Domain services (proposals, review, tasks, history, cross-vertical approval, state machines) ↔ API and auth (roll number + OTP, role checks) ↔ HTTPS ↔ mobile app (sign-in roll no. + OTP; volunteer dashboard; AH/Head dashboard + review screen; Admin view). Domain services → events → Notification service (push and OTP delivery, retry, de-duplicate) → Firebase Cloud Messaging (push) and Discord DM for OTP. SQLite is the system of record (messages, buckets, attempts, proposals, tasks, history, roster).

**Figure 2 (end to end).** AH/Head posts in a Discord group → Discord delivers the event → backend stores idempotently, maps group and sender → bucket closes (W 15, G 5, M 30, C 2) → AI relevance, one decision per message → AI drafts proposals from AH/Head messages → backend validates, resolves assignees, stores proposal PENDING → sender is notified (push), reviews, edits, accepts → backend creates task and assignee records, notifies → volunteer accepts or claims a place → does the work, marks completed → sender is notified and sees who completed what.

**Figure 3 (deployment).** Backend host (laptop or server): Discord adapter (REST polling), pipeline workers (bucketer, orchestrator), SQLite, API server (auth, domain services, notifier). Model host (Google Colab session or local machine, HTTPS, tunnel if Colab): model server (HTTP API) with a small multilingual quantized model. Phones run the mobile app (Android/iOS) over HTTPS. Backend calls FCM for push. Note on the figure: Colab sessions are time-limited, so the MVP run is best effort.

**Figure 4 (bucketing).** Join rule per message (group g, event time t): no open bucket → new bucket (s = ℓ = t). Open bucket: if t − s < M fails → new bucket; else if t − s < W or t − ℓ < G → join (ℓ = t); otherwise new bucket. End e = min(s + M, max(s + W, ℓ + G)); closes at e + C. Bucket states: OPEN → CLOSED (when e + C has passed); CLOSED → PROCESSED (stages succeed); CLOSED → FAILED (execution failure); FAILED → CLOSED (auto-retry); FAILED → AWAITING_RECOVERY (retries exhausted); AWAITING_RECOVERY → CLOSED (manual re-queue, new attempt). A message that arrives after its bucket has closed is stored and placed in a new bucket linked to the earlier one; closed buckets and their results never change. Failures are execution failures only; a failed bucket is never treated as "all messages irrelevant".

**Figure 5 (sequence).** Discord → adapter (store with dedupe, flag group and sender) → bucketer (join or start) → closed bucket → orchestrator (mask phones, emails, ID numbers) → AI relevance request → decisions → proposal request (+ context) → proposals → schema check, retry on failure → valid proposals → domain services (resolve assignees, store PENDING) → notifier ("proposal ready") → push to the sender's app only. On an execution failure: attempt FAILED_RETRYABLE, retried (fallback model if configured); after retries FAILED_PERMANENT and manual re-queue. Messages stay UNCLASSIFIED and are never recorded as IRRELEVANT. Only relevant messages from an AH or Head reach the proposal step.

**Figure 6 (review states).** As in the answer above.

**Figure 7 (task state dimensions).** Task Approval: NOT_REQUIRED, PENDING → APPROVED or DENIED (AH-raised cross-vertical task starts PENDING; same-vertical or Head-raised: NOT_REQUIRED). Assignee record Agreement: AWAITING → ACCEPTED or DENIED (EXPLICIT: one record per named person starting AWAITING; OPEN: a claim creates the record directly as ACCEPTED); set only by an in-app action, never inferred. Assignee record Work status: NOT_STARTED → IN_PROGRESS → COMPLETED (final), changed only by the assignee (or Admin). Task Cancellation: ACTIVE → CANCELLED (creator cancels; only tasks not fully completed; non-completed assignee records are cancelled and assignees notified). Rules: a task is visible to volunteers only when Approval is NOT_REQUIRED or APPROVED; an OPEN task stops taking claims when accepted = people needed (UNLIMITED never fills); two claims for the last place: exactly one succeeds; each state dimension is held in its own field.

**Figure 8 (cross-vertical approval).** AH accepts a proposal with task type CROSS_VERTICAL → backend creates the task with Approval PENDING (hidden from volunteers) → approval request (+ optional message) to the AHs and Head of the target vertical → approve or deny (+ optional message); first decision wins, later attempts see it. Approved: task goes live per assignment mode, requester notified. Denied: requester notified with message; task kept, never live. A Head-raised cross-vertical task skips approval, goes live directly, and the Head of the responsible vertical is notified.

**Figure 9 (data model).** Vertical 1–N Group 1–N Message 1–N ReactionEvent; Vertical N–N Person (roster: id, name, roll_no, discord_id, phone, role, active, reports_to → Person, verticals many); Message N–1 Bucket; Bucket 1–N RelevanceDecision (message_id, bucket_id, attempt_id, decision, model and version, correction as separate record); Bucket 1–N ProcessingAttempt (stage, model and config version, outcome, error); Bucket 1–N Proposal (type, status, primary_msg → Message, attempt_id, reviewer → Person); Proposal 1–N ProposalRevision (rev, changed_by, fields changed, time); Proposal 1–1 Task (proposal_id, creator, mode, people_needed, source and responsible vertical, cancelled, approval); Task 1–N AssigneeRecord (person_id, agreement, work_status, timestamps); Task 1–N ApprovalRequest (requester, decided_by, decision, message); Task/others 1–N HistoryRecord (entity, field, old/new, actor user or model, role and vertical at the time, time, reason/evidence); Person 1–N Notification (event, recipient, delivery_state).

**Figure 10 (AI call contract).** Backend builds the request (bucket messages, mention handles, group, vertical) → masks phones, emails and ID numbers → stateless AI layer (relevance classifier, proposal generator) → response (results, model and version, prompt/config version) → schema valid and complete? yes: store result, attempt SUCCEEDED; no: execution failure, attempt FAILED_RETRYABLE → retries left? yes: retry (fallback model if configured); no: FAILED_PERMANENT, manual re-queue. The AI layer holds no state and never writes to the database; output is advisory until the backend validates it. A malformed or incomplete output is an execution failure, never a valid empty result; a failed message is UNCLASSIFIED, never IRRELEVANT. Each call records stage, masked input reference, model and version, prompt/config version, outcome, error.
